Kindle MTP Auto-Sync Findings

Newer Kindle devices do not always mount as normal Finder volumes on macOS. Leaf should keep the existing mounted-volume sync for older Kindles and add a native MTP backend for 2024+ Kindle and Kindle Scribe devices.

Recommendation

Build native MTP auto-sync as an additive backend. Do not remove the current volume watcher. The target user experience should remain: install Leaf, plug in Kindle, Leaf syncs My Clippings.txt.

Users should not need to install Homebrew, libmtp, OpenMTP, Amazon USB File Manager, or any other separate transfer app for Leaf's own sync flow.

What Changed

Amazon's help page says Kindle Scribe and 2024-released Kindle devices on Mac require a separate application for USB file transfer, such as Send to Kindle for Mac with USB File Manager. The same page says older Kindle devices generally do not require the separate application, and Windows still exposes Kindle devices through File Explorer.

This explains the tester's issue: his Kindle charges over USB, but it does not appear in Finder. Leaf's current auto-sync depends on macOS mounting a visible volume, so it never gets a mount event and never scans the Kindle.

Compatibility Strategy

Device path How Leaf should sync Status
Older Kindle that mounts in Finder Use existing VolumeWatcher to find Documents/My Clippings.txt. Keep as-is.
Kindle Scribe or 2024+ Kindle on Mac Use a new native MTP sync backend to read My Clippings.txt directly over USB. Needs spike, then product implementation.
Device triggers both paths Deduplicate through the existing import/database path; a second import should produce 0 new highlights. Use importer result as the product-level source of truth.

Proposed Architecture

Existing path Mounted Kindle volume triggers VolumeWatcher.
New path MTP Kindle device triggers MTPKindleWatcher.
Shared import Both paths feed a local temp copy into ImportCoordinator.

The MTP layer should download only the needed file, likely /documents/My Clippings.txt or a case-insensitive equivalent, into a temporary local file. From there, Leaf can reuse the existing parser, persistence, and import status logic.

Import deduplication should stay in the existing import/database layer, not in the MTP transport layer. The MTP backend may skip a transfer optimization if the remote file metadata is unchanged, but correctness should come from importing the file and letting Leaf's existing highlight identity rules return 0 new highlights for content that is already stored.

Temporary downloads should live under a Leaf-owned directory inside FileManager.default.temporaryDirectory, for example Leaf/MTPImports/<sync-id>/My Clippings.txt. The sync operation should delete that per-sync directory with defer after import finishes. On startup, Leaf can opportunistically remove stale Leaf/MTPImports children older than 24 hours to cover crashes.

MTP Watcher Behavior

macOS does not provide a Finder-style mount notification for MTP devices. MTPKindleWatcher should use lightweight polling as the primary mechanism, then trigger immediate scans from app lifecycle events.

  • Poll for MTP devices every 10-15 seconds while Leaf is running.
  • Run an immediate scan when Leaf launches and when the Mac wakes from sleep.
  • If a low-level USB attach signal is practical through IOKit/libusb, use it only as a scan trigger, not as the only detection path.
  • Track active sync state per detected device so polling does not start overlapping imports.

The user-facing behavior remains automatic: plug in a supported Kindle, wait a few seconds, and Leaf syncs.

Detection Rule

For the spike, "detect the Kindle" should mean more than seeing any USB device or trusting a friendly device name. The minimum useful detection rule is:

  1. Enumerate an MTP device through libmtp/libusb.
  2. Read stable device metadata for logging, including vendor ID, product ID, manufacturer, model, serial number when available, and storage ID.
  3. Find a case-insensitive documents folder and a case-insensitive My Clippings.txt file inside it.
  4. Download that file and parse at least one valid Kindle clipping, or report that the file exists but contains no importable highlights.

Vendor/product IDs and device name strings are useful for diagnostics and future allow-listing, but the reliable product signal is the presence of the expected clippings file on an MTP device.

Best Technical Route

Use libmtp with libusb, wrapped by a small Leaf-owned native layer. Avoid writing a custom MTP implementation first.

  • libmtp is a purpose-built MTP library.
  • libusb supports macOS.
  • Homebrew ships current macOS bottles for libmtp, including Apple Silicon and Intel builds.
  • OpenMTP proves that MTP transfer apps are viable on macOS, but its Electron/Go stack is not a good direct fit for Leaf.

Packaging Requirement

For users, Leaf should be self-contained. Bundle dynamically linked libmtp.dylib and libusb.dylib inside Leaf.app, then configure library paths with @rpath or @executable_path.

The release pipeline needs to sign the app bundle and bundled dylibs together. If Leaf later moves to polished Developer ID distribution, this path also needs notarization verification.

License Notes

libmtp and libusb use LGPL-family licenses. That is usually compatible with a proprietary or source-available Mac app when dynamically linked, but Leaf should include license notices and avoid static linking unless the license obligations are reviewed carefully.

Remote Probe Results

A tester ran four privacy-preserving MTP probes on an Apple Silicon Mac running macOS 26.3.2 with libmtp 1.1.23 installed through Homebrew. The Kindle did not mount in Finder, but the command-line MTP tools could sometimes see it as a USB/MTP device with vendor ID 1949 and product ID 9981.

Probe Result Meaning
Original detect/list probe mtp-detect saw an Amazon Kindle MTP device, but later mtp-folders and mtp-files reported no device. Basic MTP detection works, but separate command-line sessions are fragile.
Fresh listing probe Running mtp-files first after a fresh plug-in listed the device and found My Clippings.txt at 3,050 bytes. The affected Kindle does expose the target clippings file over MTP.
Download probe without Kindle restart mtp-files could not see the device. The MTP state can remain wedged after previous sessions; sleep/wake or replug alone may not be enough.
Download probe after Kindle restart mtp-files again found My Clippings.txt, this time with file ID 2, but mtp-getfile then reported No devices. File IDs are per-session and unstable, and a second CLI process cannot be trusted to reopen the Kindle for download.

Current Conclusion — October 9, 2026

Native MTP download is proven on the tester's Kindle Scribe: the fixed helper found and downloaded My Clippings.txt in one opened session, returned exit 0, and deleted the raw file after summarizing it. This is a successful transport spike, not an integrated Leaf feature or a full parser test.

Native Download Findings and Agent Handoff

The controlled comparison used separate fresh Kindle restarts for standard mtp-files and Leaf's helper. In mtp-kindle-comparison-20261009-090639, the standard tool exited 0 and found the clippings; the original helper exited 12 without downloading anything.

Root cause: scripts/probe_mtp_kindle_native.c opened the device with LIBMTP_Open_Raw_Device_Uncached but called the cache-based LIBMTP_Get_Filelisting_With_Callback. With an empty cache this returned no files without issuing a file-enumeration request. This was an API mismatch in our helper, not proof the Kindle could not transfer files. Commit f7d14fd replaces this with recursive LIBMTP_Get_Files_And_Folders calls, matching upstream mtp-files. It scans each storage, preserves the matching file ID, frees enumeration entries, and downloads through LIBMTP_Get_File_To_File in the same session.

Remaining implementation work

  • Integrate the proven transport into Leaf's existing import pipeline, preserving mounted-volume sync for older Kindles and existing database deduplication.
  • Run blocking USB work off the UI thread; handle contention, unplugging, failures, and temporary-file cleanup.
  • Test repeated syncs and reconnects without mandatory Kindle restarts; investigate release/reset behavior.
  • Bundle and sign the native helper and dependencies so normal users need only Leaf. Validate on a clean Mac without Homebrew and expand device coverage.
  • Verify actual parser/import output and end-to-end auto-sync; the spike only counted separators and metadata lines.

Main Risks

  • Device quirks: MTP devices can behave inconsistently, and libmtp has documented device-specific issues.
  • Device contention: Amazon USB File Manager, OpenMTP, Calibre, or another MTP app may already hold the device connection.
  • Packaging: Bundled dylibs must be signed, loaded correctly, and tested on clean Apple Silicon and Intel Macs.
  • Sandboxing: A sandboxed build may need the macOS USB device entitlement. Current GitHub-style distribution is likely simpler than Mac App Store distribution.

Decision Gate

The native transport portion is proven. The next gate is end-to-end Leaf import and repeated-connection reliability:

Plug in a 2024+ Kindle on Mac -> enumerate MTP device -> find documents/My Clippings.txt -> download to temp -> parse -> delete temp file

Proceed with Leaf integration using the proven helper API; retain the older mounted-volume backend.
